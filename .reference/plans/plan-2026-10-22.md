# Plan, 22 October 2026: the Figma side, in five panes

Phase 1 of the round: findings, a design, work units. Nothing in the repository was changed to write it, except a
new section 15 in `.reference/figma/measured_behaviour.md`, the record of a read-only probe.

It carries out the maintainer's rulings: the cast of five objects, the field writer, five panes, the lock in the
file, and the blueprint (designed here, built only as far as the Build pane needs). Line numbers are those of the
`loading-chapter` branch at `19affbf`. Phase 2 starts after that branch merges; section 5 says which units need it.

## 1. Findings

### 1.1 Where the Figma side still computes what the core answers

After the 21 October switch the parts, axes, twins, rests and `applies()` all come from the core (`folds.ts:61-107`,
`designSource.ts:66-117`). What is left:

1. **The plugin never calls `load()`.** The screen sends one file's text (`ui/components/pane-system.js:277,301-304,357-366`,
   single file, `files[0]`); the main thread runs `JSON.parse` and `new Resolver()` (`main/handlers/loadDocument.ts:68-117`).
   So only a self-contained resolver document loads: no token file, no list, no overrides map, no external `$ref`,
   no `reads`, no `origins`. **A message is now false:** `looksLikeTokenFile` and `WRONG_FORMAT`
   (`loadDocument.ts:157-197`) tell a person that a DTCG token file cannot be loaded. Since the loading chapter the
   core loads one. This is the fix R13 was written about (smell #29), now pointing the wrong way.
2. **The command line drops what `load()` answers.** `cli/run.ts:64-74` calls `load(entry, { read })` with one path
   and sends `JSON.stringify(document)`: `reads`, `overrides` and `origins` are lost, no list, no `name`, no map.
   `cli/main.ts:58` takes one positional as the resolver. `cli/check.ts:26-27` loads, stringifies, parses and builds
   a resolver: a round trip for nothing.
3. **Lookup paths sliced by hand.** `sum.ts:271,273,304`, `purpose.ts:141`, `folds.ts:157`,
   `designSource.ts:100-109` slice `dsName.length + 1` off a path; the core answers with `referencePath()`.
   `main/components/file.ts:126-127` walks every path of every mode to ask whether a name is a token; the core
   answers with `getNodeKind()`.
4. **The default mode taken as the first.** `resolverModes.ts:131` and `sum.ts:245` use `modeNames[0]`; the core
   answers with `getDefaultMode()`. True today only because the sum puts the defaults first.
5. **A raw chain step normalized by the adapter.** `sum.ts:465,469` call `normalizeTokenValue()` with a type the
   adapter found itself; `valueAt()` answers it. Same finding as postcss's finding 5 of 21 October; the lib parked
   it (question 9 there). Left as is unless the lib's gated unit 11 is ruled in.
6. **A copy of the core's reference grammar.** `shared/components/axes.ts:263`, `BRACED`, is the core's `REFERENCE`
   byte for byte; `referencesIn()` gives each reference's written text. Whether the core's grammar accepts the
   `(input)` segment form is not checked; the unit checks it before swapping.
7. **Paths in any mode, walked four times.** `resolverModes.ts:151-203`, `designSource.ts:53`,
   `handlers/tokenGraph.ts:37-63`, `utils/buildPayloads.ts:25`. The core has the walk privately
   (`toghen-lib/src/core/collection.ts:900`, `tokenPaths('', undefined)`) and does not export it. One consumer
   (this adapter), so by the lib's rule it stays here, once.
8. **Kept, correctly:** who refers to a token (`sum.ts:222-234`, `tokenGraph.ts:65-84`), the review's question 20,
   one consumer; built twice in one adapter, so one copy, not two. `${modifier}=${context}` strings at
   `sum.ts:326,416,419,487` are message locators, not mode names. `flattenDesignSystem.ts:12-16` cites the removed
   `ds.entries`: a stale comment.

### 1.2 Where the field table and the roster disagree

The field table, `shared/components/fields.ts:31-53`, has four columns: the layer kinds, the value kind, the options,
and the property type a field may be wired to. **It has no binding column.** Whether a field binds, with which call,
to which variable type and scope, and whether Figma reports it on parts, is spread across about ten places:
`apply.ts:330,331,337,351,385-386` (field lists), `boundVariables.ts:7,13-16` (`PAINT_PROPERTIES`, `BOUND_BY_PARTS`),
`groups.ts:76-85` (`scopesOfField`, regexes that list the fields again), `receipt.ts:46-71,89-115` (if-chains per
field), `styleSyncEngine.ts:137-153` and `operationExecutor.ts:67-74` (text and effect fields of styles),
`shared/conventions.ts:10-28` (the conventions' free-text property names), `purpose.ts:23-49`.

Against the roster (`.reference/figma/property_roster.md`):

1. **Bindable, and not bound.** `counterAxisSpacing` (roster line 59), the only bindable layout field Toghen lacks.
   Effects as fields: shadows' five fields and blurs' radius (119-120). The text fields: `fontFamily`, `fontStyle`,
   `fontWeight`, `fontSize`, `lineHeight`, `letterSpacing`, `paragraphSpacing`, `paragraphIndent` (133-141), which
   reach a text only through `textStyle` today. Layout grids (162-163). `visible` (90) and `characters` (132), which
   the table has as plain values. Instance properties and property defaults (173-174), plain only.
2. **A paint's alpha is dropped.** `apply.ts:91-93` binds a solid paint's red, green and blue and drops the
   variable's alpha; a hex alpha becomes the paint's opacity (`apply.ts:83`). The roster's warning at line 189.
3. **A gradient has no field.** A `gradient` token goes to a paint style (`tokenTypeMap.ts:20`), but no field names a
   fill style, and the roster shows a gradient stop binds by writing the alias into the stop (measured §14).
4. **Writes outside the table and outside every receipt.** `apply.ts:344` (`fills = []`), `:347` (a line's
   `strokes = []`), `:353` (`strokeAlign = 'INSIDE'` whenever a side's weight is declared), `:356`
   (`strokeWeight = 0`). The roster calls `strokeAlign` uncovered; Toghen writes it anyway and never sees a hand edit
   of it.
5. **Kinds.** The roster counts an `INSTANCE` among the frame kinds (line 16); the table's container group leaves it
   out (`fields.ts:56`), deliberately (`check.ts:36`). The roster's summary (207-215) names only strokes and effects
   as missing on an instance. `strokeWeight` lists `TEXT` in the roster (106) and not in the table.
6. **One error in the roster:** line 53 says `SPACE_EVENLY` and `SPACE_AROUND` are only in Toghen's table; typings
   1.139.0 declare both (`plugin-api.d.ts:7815-7816`).
7. **One error in the code:** `check.ts:122` accepts `width=#null`, and `apply.ts:314-331` ignores it.
8. **The roster cannot say what Toghen does with a field.** Its Toghen column (legend, line 22) says whether the
   table offers a field, not whether Toghen binds it, writes it as a value, or writes it plain. `visible` and
   `characters` read "Yes" and are never bound. The column needs that third word.
9. **No DTCG type carries a boolean or a string.** The type map has `string` and `boolean`
   (`tokenTypeMap.ts:17-18`), which the format does not define. So binding `visible` or `characters` serves only a
   document that uses those types. Noted, not a defect.

### 1.4 What the stamp and the lock rulings imply for the sync-state code

- **The root holds two things today:** kept templates (`toghen/templates`, sharded, `templateStore.ts:13`) and the
  old root record, read and deleted by `rootRecord.ts:25,38-88`. Nothing else writes there. The lock is the third
  thing, and the second live one. It goes through `shardedData.ts`, as templates do: a library of a few hundred
  components passes Figma's 100 kB per entry at about 1,500 keys, so sharding is a real need.
- **The lock is not a ledger.** It holds what a name resolved to (a key), never what Toghen wrote (no hash, no
  receipt). Receipts stay one per object. The stamp ruling stands.
- **The stamp holds no key.** `Identity` (`stamp.ts:44-59`) has none; a member's receipt hashes its main component's
  node id (`receipt.ts:28-29,55,112`). So when the lock sends a name to another key, the imported component has
  another id, the receipt no longer matches, and the diff already puts `component` among a layer's fields to write
  (`diff.ts:300-323`); the update swaps (`update.ts:239-246,332`). **The relink needs no new comparison**; it needs
  the locator to answer through the lock, and its own step so each swap is one row.
- **Components resolve locally only.** By name, exactly one, across every page (`resolve.ts:308-333`), or by a
  `(key)` written in the file. Tokens resolve by variable name in local collections only (`resolve.ts:170-180`). A
  consumer of a library has neither locally.
- **Two migrations still run.** The root record's (`rootRecord.ts`, on every load) and the six old node keys'
  (`stamp.ts:133,174-181`). No sunset is written down. Not touched this round (question 13).
- **Smaller:** `shardedData.ts:18-19` names `tokenStamps.ts` where it means `rootRecord.ts`.

### 1.5 The API for discovery: what was measured, what is not

Read from the typings (`@figma/plugin-typings` 1.139.0):

- `figma.teamLibrary.getAvailableLibraryVariableCollectionsAsync()` lists collections in the **enabled** libraries,
  each with `name`, `key` and `libraryName`; `getVariablesInLibraryCollectionAsync(key)` lists `name`, `key`,
  `resolvedType`. There is **no listing of library components or styles**: they import by key only
  (`importComponentByKeyAsync`, `importComponentSetByKeyAsync`, `importStyleByKeyAsync`).
- The manifest needs `"permissions": ["teamlibrary"]` (`manifest_section.md:268`). Toghen's has no permissions.
- `figma.fileKey` is for private plugins only, with `enablePrivatePluginApi` in the manifest, which also works for
  a development plugin (`manifest_section.md:245-246`). A public plugin cannot read its own file's key.
- `getPublishStatusAsync()` on a component, style or variable answers `UNPUBLISHED`, `CURRENT` or `CHANGED`.

Measured on 22 October (`measured_behaviour.md` §15, read-only, in `TEST_GROUIND` through the connector):
`teamLibrary` exists and lists nothing in that file; `figma.fileKey` reads (the connector is privileged, so no proof
for the plugin); `figma.root.name` reads `Document`, not the file's name; every local object has a 40-digit key,
published or not; `getPublishStatusAsync()` answers locally (`UNPUBLISHED`); **an unpublished key does not import,
even in its own file, and the error is the one a key that never existed gives** (`Component with key "…" not found`).

So "publish it" cannot be read from a failed import. It can be read in the library file, from the publish status,
by the run that built it.

**Measured on 22 October, second pass** (`measured_behaviour.md` §15, *Second pass*), with a library published from a
second file but **not enabled** in `TEST_GROUIND`:

2. **A published library's variables, components, sets and styles import by key without being enabled**, each with
   `remote` true; enabling matters for `figma.teamLibrary`'s listing only.
3. **A variable's id is stable, its object is not**: two imports of one key give one id but `===` is false. A component,
   set or style gives the same object within a call. Variable and style ids survive the import being dropped and made
   again; a component's node id does not.
5. **`importStyleByKeyAsync` returns a style with `remote` true that binds like a local one** (`textStyleId` reads it
   back); an imported variable binds to a fill like a local one.

Also found: **a style has no `getPublishStatusAsync`**, local or imported (`TypeError: not a function`), against the
typings; an imported variable or collection throws on it (`can only query publish status for local variables`), an
imported component reads `UNPUBLISHED`; a variant reads `UNPUBLISHED` in its library while its set reads `CURRENT`,
and still imports by its own key; an imported collection's `variableIds` lists only what the file has imported so far;
imported objects refuse `remove()` (`in remove: Removing this node is not allowed`) and drop out on their own once
unused.

**Measured on 22 October, third pass** (§15, *Third pass*), with the library enabled:

1. **A listed collection is exactly `{ name, libraryName, key }`, and `libraryName` is the library file's name**; a
   listed variable is exactly `{ name, resolvedType, key }`, in an order that is not the library's. An unknown
   collection key resolves to `[]` rather than rejecting. Enabling changes nothing about import by key, `remote` or ids.

**Still unmeasured:**

4. Whether the keys survive a republish, and a set's a rebuild in place. Every key is recorded in §15 for the
   comparison; the republish is the maintainer's.
6. In the desktop plugin, not the connector: whether `figma.teamLibrary` needs the `teamlibrary` permission, and what
   `figma.root.name` reads.

## 2. The design

### 2.1 Load: the composition, and the overrides map named once

The plugin calls the core's `load()`, as the command line does. It never reads files itself.

```typescript
// shared/protocol.ts: replaces { json, fileName?, dryRun? }
LOAD_DOCUMENT: {
  files: { path: string; text: string }[];   // every file picked, by its path relative to the pick
  entry: string | string[];                  // a resolver document, one token file, or several in order
  name?: string;                             // token files only; the screen always sends one (below)
  overrides?: Overrides;                     // a $ref as written → the location to read instead
  dryRun?: boolean;
}

/** One shape, used twice: files in Load, Figma objects in Build. A name as written → what to use instead. */
type Overrides = Record<string, string>;
```

- **`read`** is a lookup among `files` by path. A missing file is the core's error, naming the reference and its
  holder. A folder pick (`<input webkitdirectory>`) gives each file its relative path, so a resolver document's
  `$ref`s to sibling folders resolve; a flat pick gives bare names.
- **The name.** The core defaults a token file collection's name to the files' folder. A flat pick has no folder,
  so the core would refuse. The screen sends a name always: from a folder pick, the folder's name; from a flat
  pick, the first file's name without its extensions. It is an editable field shown before Load (R10).
- **The composition** is what the Load pane draws, and what the payload carries beside the document's state:

  ```typescript
  composition: {
    form: 'resolver' | 'tokens';
    entry: string | string[];
    reads: LoadResult['reads'];             // ref as written, holder, location, overridden
    overrides?: { map: Overrides; hash: string; unused: string[] };
  }
  ```

  Collisions are a load's output, so they go to the result surface, one row each (R2, R14), a differing one marked
  as a problem and a redundant one quiet (R4). The overrides map's table is drawn from `reads` where `overridden`,
  plus the unused keys as rows that matched nothing.
- **Recents** keep the bundle (`load`'s `document`, self-contained) and the composition, not the picked files: a
  recent row reloads without the files, and the pane says it was loaded from the bundle.
- **The command line**: every `.json` positional is the entry, one or several, in order; `.kdl` positionals are
  blueprints and component files, as now. `--name <name>` and `--overrides <map.json>`. It sends the bundle and the
  composition, so the screen shows what the command line loaded.
- **The overrides map in Build** is the same shape: a component or library name as a blueprint writes it, to the
  name or key to use instead (2.3). One type, one table on screen, drawn by one component.

### 2.2 The field writer

**The table.** `FieldSpec` grows one optional column, `token`, taken from the roster. A field without it takes no
token (an enum, a structure, a component).

```typescript
// shared/components/fields.ts
interface FieldSpec {
  nodes: readonly LayerKind[];
  value: ValueKind;
  options?: readonly string[];
  wires?: PropertyType;
  /** How a token reaches this field: the roster's Bind and Token columns. */
  token?: {
    types: readonly string[];              // the token types it carries: 'dimension', 'number', 'color', …
    bind?: {                               // absent: written as the resolved value, following one context
      call: 'field' | 'paint' | 'effect' | 'grid' | 'text' | 'property';
      field: string;                       // the name the binding call takes
      variable: VariableResolvedDataType;
      scope?: VariableScope;               // the picker it is offered in
      parts?: readonly string[];           // reported on these, not on the field: corners, sides
    };
  };
}
```

`call` names the Plugin API call: `setBoundVariable`, `setBoundVariableForPaint` (or the alias written into a
gradient stop), `setBoundVariableForEffect`, `setBoundVariableForLayoutGrid`, a whole-text `setRangeBoundVariable`,
`setProperties` with an alias. `scopesOfField` (`groups.ts:76-85`), `BOUND_BY_PARTS`, `PAINT_PROPERTIES`, the field
lists in `apply.ts` and the receipt's if-chains are derived from the table and deleted.

**The one function.**

```typescript
// main/components/fieldWriter.ts
function writeField(node: SceneNode, field: string, value: Value, resolved: Resolved): Written;

type Written =
  | { how: 'bound'; variable: Variable }
  | { how: 'value'; context: string }      // a token on a field Figma cannot bind: its value, in this context
  | { how: 'plain' };                      // a literal
```

The rule, once: **a token on any field; bound where Figma can bind it; written as its resolved value where it
cannot, said once in the report; a written value follows one context only, and the report says which.** Its read
twin, `reportField(node, field)`, gives the receipt what Figma reports, reading parts as the table says. The receipt
rule for parts extends: a paint reads per paint (as now), an effect per effect and field, a text field per range
(bound when every range names one variable, as corners are when every corner does), a layout grid per grid and
field.

**Which context a written value takes** is a choice made for the person (R10), so it is on screen before Build or
Apply runs. Recommended: the core's answer at the declared defaults (`getDefaultMode()`), named in the report as
the defaults' mode name. The alternative is the context the layer's pinned modes name; see question 4.

**Implicit writes** (finding 1.2.4) become declared: `strokeAlign` is a field; a side's weight no longer sets it;
`strokeWeight = 0` and the cleared white fill of a new frame stay creation steps, not field writes, and are said in
the specs as such.

**Fields added**, each with its row in the table, as the roster gives it:

| Area | Fields | Token |
|---|---|---|
| Wrap | `layoutWrap`, `counterAxisAlignContent` | none (enums) |
| | `counterAxisSpacing` | dimension, bound, `GAP` |
| Grid child | `gridChildHorizontalAlign`, `gridChildVerticalAlign` | none |
| Position | `layoutPositioning`, `constraints` | none |
| | `x`, `y` | dimension, written as a value |
| Appearance | `blendMode` | none |
| | `cornerSmoothing` | number, written as a value |
| Strokes | `strokeAlign`, `strokeCap`, `strokeJoin` | none |
| | `dashPattern` | `strokeStyle`'s dash array, written as a value |
| Paints | a gradient in `fills` and `strokes` | each stop's colour bound; positions and angle written |
| Effects | `effects`: a list of shadow and blur tokens | each shadow's five fields bound (`EFFECT_COLOR`, `EFFECT_FLOAT`), a blur's radius |
| Text | `fontFamily`, `fontStyle` | `fontFamily`, string; bound, `FONT_FAMILY`, `FONT_STYLE` |
| | `fontWeight`, `fontSize`, `lineHeight`, `letterSpacing`, `paragraphSpacing`, `paragraphIndent` | bound, whole text; a line height or letter spacing binds as pixels only (roster 138-139), so a unitless line height or an `em` spacing is written as a value |
| | `textAlignHorizontal`, `textAlignVertical`, `textCase`, `textDecoration`, `textTruncation`, `leadingTrim` | none |
| | `maxLines`, `listSpacing` | number, dimension; written as a value; `maxLines` after `textTruncation` (measured: it is dropped otherwise) |

| Existing | `visible`, `characters` | bound to a `boolean`, `string` token where one is given |

Left out, as the roster says no token carries them and nothing asks: `itemReverseZIndex`,

### 2.3 The lock

**The record**, on the file's root, `toghen/lock`, sharded through `shardedData.ts`:

```typescript
interface Lock {
  libraries: Record<string, LockedLibrary>;     // keyed by library name, as Figma names it
  overrides?: Overrides;                        // Build's map: a name as written → the name or key to use instead
}

interface LockedLibrary {
  fileKey?: string;                             // when someone could know it (below); never guessed
  by: 'discovery' | 'build' | 'command line' | 'person';   // who wrote the entry last (R11)
  components: Record<string, { key: string; set: boolean }>;   // a component's name as blueprints write it
  styles: Record<string, { key: string; kind: 'TEXT' | 'EFFECT' | 'PAINT' }>; // a token path
  variables: Record<string, string>;            // "<collection>/<variable name>" → key
}
```

No hash, no time, no receipt. It records what a name resolved to.

**Three fillers, asymmetric as the API is.**

1. **Variables, by discovery.** In the consumer file: list the enabled libraries' collections; for each token a
   blueprint binds, the collection and variable name the variable sync would give it (the sum and
   `tokenPathToVariableName()`, already one function); match by both names; write the keys under the library's
   name. Import happens at build, by key. Two libraries with a match is a choice: listed, never picked (R10); the
   person names one in Build's overrides map. Needs the `teamlibrary` permission.
2. **Components and styles, by the run that built the library, or by the command line opening both files.** No API
   lists a library's components. The library file knows its own keys (`node.key`) and publish status. So the
   command line pairs twice, once with the plugin in the library file and once in the target (two codes, printed
   with which file each is for). After a build in the library file, or with no build, it asks the library plugin
   for its stamped sets' names, keys and publish status, and sends them to the target plugin, which writes the
   lock (`by: 'build'` or `'command line'`). Each set whose status is not `CURRENT` is a "publish it" line in the
   report: *"Core" changed since it was published: publish the library, then accept the update in this file.*
3. **By a person picking once.** In the Build pane, for a missing component: place one instance from Figma's assets
   panel, select it, press **Use the selected instance**. The plugin reads its main component's key and its
   library name where the API gives one, and writes the entry (`by: 'person'`). A library name it cannot read is
   asked for in the same row.

**The file key.** Only a private plugin, or a development plugin with `enablePrivatePluginApi`, can read it. The
lock does not depend on it; the run that built the library writes it where it can read it (question 1).

**The locator** answers in this order, and never falls back: a name in Build's overrides map is replaced first, as
a `$ref` is in Load; a name declared from a library resolves through the lock; any other name resolves locally, as
today. A name found both locally and in a declared library stops the build, naming both, as a token whose name is
in two collections does today.

### 2.4 The relink step

A relink is the existing swap, driven by the lock. For every stamped instance a run reconciles, its component's
name resolves through the locator; the imported component's id differs from the receipt's, so the diff already
plans the write. What changes:

```typescript
// shared/components/steps.ts, beside PATCH_LAYER
| { kind: 'SWAP_COMPONENT'; member: string; memberId: string; nodeId: string; component: string;
    from: string; to: string; library?: string }   // one per instance: one row (R14)
```

The diff emits it in place of `component` among a `PATCH_LAYER`'s fields; the update calls the existing
`swapComponent`. The Build pane's **Plan relink** runs a dry build of every kept blueprint and component file and
shows only these rows and the "publish it" lines (R6: `relink plan`). An instance a person placed carries no stamp
and is not relinked; the report counts them once, *n instances not made by Toghen were left*.

The seam that stays human: a key imports only once published, and a consuming file sees a new version only once a
person accepts it (`measured_behaviour.md` §7, *Libraries*).

### 2.6 The blueprint

A page is the unit. One kdlet document, `<page>.blueprint.kdl`, folds component files and artboard files together
and declares what it needs.

```kdl
page Buttons

tokens "tokens/ds.resolver.json" overrides="themes/warm.overrides.json"
library Core

component Button tokens="{button}" {
    properties {
        VARIANT Tone calm loud
    }
    FRAME Button layoutMode=HORIZONTAL itemSpacing="{space.sm}" {
        INSTANCE Icon component=Icon        // from Core, through the lock
    }
}

artboard "Button reference" {
    FRAME Page layoutMode=VERTICAL {
        INSTANCE Set component=Button
    }
}
```

- **`page <Name>`**, exactly one: the Figma page the blueprint builds into, created if missing.
- **`tokens <entry>… [name=…] [overrides=…]`**, at most one: the three forms of `load`, as the command line takes
  them. In the plugin, a blueprint's `tokens` is held against what Load loaded, by entry name and map hash; it
  reads no file.
- **`library <Name>`**, any number: a library whose components, styles and variables this page names. A component
  name resolves through the lock only for a declared library.
- **`component <Name> … { … }`** and **`artboard <Name> { … }`**, any number: the body is today's component file or
  artboard file, minus its header line. Components come first in a run, then artboards, as today.
- `guard` and `define` at the top are shared by every body below them, as kdlet's scope gives.

**The reader** reads the four words that are the blueprint's and hands each body to the existing readers
(`readComponentFile`, the artboard reader), so a blueprint is checked exactly as its files would be. A component
file and an artboard file stay readable on their own: a blueprint of one component is not required.

**Built this round:** the reader of the four words, and the needs (`tokens`, `library`, every component name the
bodies use, resolved by the locator in a dry pass): found, would swap, missing. Keeping a blueprint in the file, as
a template is kept. **Not built:** building a blueprint as a whole (each body still builds through today's entry,
one at a time), a blueprint from the command line, the page created by a run.

## 4. Risks and questions for the maintainer

Blocking, before Phase 2:

1. **The file key.** A public plugin cannot read it; a development plugin can, with `enablePrivatePluginApi`.
   Recommended: the lock is keyed by library name and holds the file key only where a run could read it; set
   `enablePrivatePluginApi` while the plugin is in development, and record that a published plugin would lose it.
2. **The `teamlibrary` permission** in the manifest. A manifest change shows a person a permission. Recommended:
   add it.
3. **A published library for the probe.** Section 1.5's six questions need a second file published as a library and
   enabled in `TEST_GROUIND`, by a person. Recommended: unit 11 builds against the typings and the mock, its tests
   marked *unmeasured* where §15 is silent, and the probe runs when the library exists.
4. **The context of a written value.** (a) The core at the declared defaults, the same in every member, named in the
   report. (b) The context the layer's pinned modes name, mapped back through the sum's mode names. (c) Figma's own
   `resolveForConsumer` on the token's variable, which follows the pins but needs a variable and is Figma's answer,
   not the core's. Recommended: (a) now, (b) when a member's pin makes a written value wrong for someone.
5. **R8's spot, and the map.** R8 names *the Design System pane*. Recommended: the spot becomes *the Load pane*,
   limit and reason unchanged, and the Sync pane's tab is inert with nothing loaded, as Tokens' is. Needs sign-off,
   as a rule change.
6. **Apply.** (a) The query is over tokens, not layer names: confirm. (b) Apply's writes carry no stamp, so on a
   built component they read as drift on the next build. (c) The conventions card stays in Apply. Recommended: all
   three as written.
7. **Variables in the lock**, or only discovered on every run. Recommended: in the lock, so a run in a file where the
   library was disabled still imports by key (unmeasured: question 1.5.2).
8. **Library styles** have no discovery, so they are filled as components are. Confirm.
9. **A name in a declared library and locally** stops the build. Confirm, or rule that the declared library wins.

Can default if not answered:

10. `string` and `boolean` token types on `visible`, `characters` and instance properties: bound where a document
    has them. Default: yes; Toghen adds no type.
11. A text field beside `textStyle`: refused, naming both. Default: refused; an override of a style is a second
    source for one value.
12. The blueprint's extension, `.blueprint.kdl`, and that component and artboard files stay readable alone. Default:
    yes.
13. The two migrations (the root record, the old node keys): kept. Default: kept; a sunset is its own ruling.
14. Build's overrides map lives in the lock's record, on the root. Default: yes.
15. A gradient on `fills` binds its stops, and the fill-style field stays absent. Default: yes.

- **Shared files across parallel units.** `fields.ts`, `check.ts`, `component-files.md` and the roster in units 3,

- **The lock and the relink touch other people's files' instances only through a file's own stamped instances.**

- **FigCraft** has no library model in this design. The field writer is Figma's; FigCraft's variables and styles go
